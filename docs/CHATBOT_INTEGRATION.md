# Chatbot Integration (Architecture A — Groq Tool-Calling Assistant)

The chatbot is a **read-only natural-language layer on top of the existing Graph 1/2/3
APIs**. It adds zero new numerical logic: every number the assistant quotes comes from
a tool response generated by the same handler functions the dashboard and any
production frontend already call. This document is the contract for the Streamlit
widget (implemented) and for a future React/Next.js client.

```
User question
     │
     ▼
POST /api/chat  ──►  chat_router  ──►  agent.run_chat()
                                          │
                       system prompt + last N messages + question
                                          │
                                          ▼
                            Groq LLM (llama-3.3-70b-versatile,
                            fallback llama-3.1-8b-instant)
                                          │  tool_calls (≤ CHAT_MAX_TOOL_ROUNDS)
                                          ▼
                        chatbot/tools.py executors  ── call ──►
                        ap_retail_graph / state_comparison_graph /
                        supply_balance_graph / history loaders /
                        ingestion_status / get_latest_forecast
                                                    (in-process, read-only)
                                          │
                        compact (token-guarded summary) → back to the LLM
                        full payload         → "chart" in the response
                                          ▼
                 markdown answer + optional chart + warnings
                 persisted to MongoDB (chat_sessions / chat_messages)
```

## Endpoints

All endpoints inherit the app-wide `/api/*` Bearer-token middleware
(`Authorization: Bearer <API_BEARER_TOKEN>`).

| Method | Path                | Purpose |
|--------|---------------------|---------|
| POST   | `/api/chat`         | One chat turn (blocking). Primary path. |
| POST   | `/api/chat/stream`  | SSE: `thinking` → `chunk`* → `chart` → `done`, or `error`. |
| GET    | `/api/chat/sessions`| Recent conversations (`limit` ≤ 100). |
| GET    | `/api/chat/history` | Full message list of one session (`session_id` required). |

Status codes: `200` ok · `401` bad/missing token · `404` session not found (history) ·
`422` invalid input (empty/over-long message) · `429` upstream rate limit surfaces in the
message via fallback chain · `500` unexpected · `503` chat disabled or `GROQ_API_KEY`
missing/unreachable (message tells you exactly what to set).

## POST /api/chat

Request:

```json
{"message": "What will AP retail onion prices be next week?",
 "session_id": null,          // optional; server creates a session when omitted
 "wants_chart": null}         // optional hint; charts are attached by tool use
```

Response (exact keys, `chart` is `null` when no forecast tool ran):

```json
{
  "session_id": "…hex…",
  "answer": "markdown text …",
  "answer_format": "markdown",
  "chart": { "graph": "ap_price_forecast", "...": "same JSON contract as FRONTEND_INTEGRATION.md" },
  "chart_display": "collapsed",
  "tools_used": ["forecast_ap_prices"],
  "session_title": "What will AP retail price…",
  "warnings": []
}
```

`chart` payloads reuse the Graph 1/2/3 JSON contracts verbatim (`graph` field:
`ap_price_forecast` | `state_price_comparison` | `supply_demand_shortfall`), so the same
renderer used for the graph endpoints can draw them behind a collapsed toggle.

## The 7 read-only tools

| Tool | Wraps | Notes |
|------|-------|-------|
| `forecast_ap_prices` | `GET /api/graphs/ap-retail` handler (`main.ap_retail_graph`) | predicted price, lower/upper bounds, confidence score |
| `forecast_state_comparison` | `GET /api/graphs/state-comparison` handler (`main.state_comparison_graph`) | any of AP/KA/MH/MP |
| `forecast_supply_balance` | `GET /api/graphs/supply-balance` handler (`main.supply_balance_graph`) | predicted quantities and lower/upper bounds; **AP only** (tonnes/month) |
| `factors` | forecast input definitions in `main.py` | explains the historical price/arrival context and external factors not used as separate inputs; does not claim causes |
| `get_price_history` | history loaders | daily prices or monthly quantities |
| `data_freshness` | `main._status` + `ingestion_status()` | staleness + last ingestion log |
| `get_saved_forecast` | `history_store.get_latest_forecast()` | repeats the last saved run |

There is **no ingestion-trigger tool by design**. If data looks stale, the assistant only
*reports* it and points to the scheduled 6-hourly task or `pull_upag_dash.py --once`.

## Anti-hallucination rules

1. Numbers may only come from tool compacts (the message `role:"tool"` content).
2. After generation, quoted ₹/% tokens are verified against those compacts; anything
   unverified is replaced with `…` and a warning is added. Tolerant matching (≈1%)
   avoids false redactions from formatting differences.
3. The system prompt uses plain-language forecasts: predicted price/value, lower
   bound, upper bound and the confidence score when available. It avoids internal
   percentile terminology and does not discuss score methodology.

## Persistence

Same MongoDB store as the rest of the app (`MONGO_DB_NAME` from `config/.env`), two
collections:

- `chat_sessions` `{session_id, created_at, updated_at, user_label, title, messages_count}` (unique index on `session_id`)
- `chat_messages` `{seq, session_id, role 'user'|'assistant', content, tools_used JSON string, chart_kind, created_at}` (indexed `(session_id, seq)`)

`seq` is the per-message sequence number generated by the app-managed `counters`
collection; the API serializes it to clients as `id` (same field name as before the
storage migration).

Chart payloads are **not persisted** (they are live Computations); titles auto-set from the
first user message (≤ 48 chars).

## Streamlit widget

`dashboard.py` (appended block, existing sections untouched): a fixed, labeled **💬 Ask Onion AI**
button at the bottom-right toggles a floating panel (session picker, chat bubbles, input).
The high-contrast pill remains visible against the dashboard and uses a clear close label
while the panel is open. The chat history scrolls independently so the message composer
stays visible after long answers. Charts render
only inside a collapsed `“📊 Show forecast chart”` expander. When the backend answers
`503`, the panel surfaces the hint instead of a stack trace.

## CORS

The app-wide CORS middleware applies to the chat routes too. By default
`CORS_ORIGINS` is unset, which permits every origin (`*`): any browser page may call the
chat endpoints, and preflight `OPTIONS /api/chat*` is answered without a bearer token.
Cookies are not part of the auth flow (`allow_credentials=False`) — callers authenticate
with the `Authorization: Bearer <API_BEARER_TOKEN>` header exactly like every other
`/api/*` route, which a browser sends only through its own backend proxy.

For a public deployment, set `CORS_ORIGINS` to the comma-separated web origins that
should be allowed (e.g. `http://localhost:3000,https://dashboard.example.com`); responses
then echo the allowed origin instead of `*`, and other origins are blocked by the
browser. CORS is not authentication — it does not weaken or replace the bearer-token
middleware. See `API.md` (`CORS (cross-origin browser calls)`) for the full behavior.
